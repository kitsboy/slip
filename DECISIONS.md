# Decisions

Every deviation from the build spec, and every assumption made where the spec was
silent, lands here in the same commit that makes it. Spec: `MASTER-BRAIN/03-Projects/slip/SLIP-PLAN.md`.

---

### D-01 — React 18 + Tailwind 3 instead of Alpine/Preact (spec §2)
Cam's explicit call. Cost: ~45 KB gzip of the bundle. Benefit: familiar, hireable,
and the state complexity of a cart + payment engine + admin drawer justifies it.
Measured at P0: whole app is 152 KB raw / 49 KB gzip single file.

### D-02 — Tailwind 3.4, not the CDN, not v4
The CDN script is banned outright (needs network, needs `unsafe-eval`). Tailwind 4
was skipped for v1 because its PostCSS plugin story churns; 3.4 is pinned and
stable. Revisit only if a real need appears.

### D-03 — No byte-identical rebuild claim (spec §17.16)
Dropped. Modern bundlers embed content hashes and timestamps; promising
reproducibility would be a lie. What we DO ship: exact pinned dependency versions,
a committed lockfile, and a published `SHA256SUMS` for every release so two builds
can be compared by a human.

### D-04 — No in-file self-integrity hash (spec §7.9)
Dropped as impossible: a file cannot contain the SHA-256 of itself. Replaced with
the honest equivalent — the build prints the hash, `dist/SHA256SUMS` carries it, and
the About screen shows the same value for the merchant to compare against whatever
they downloaded.

### D-05 — CSP is injected at build time only
The Vite dev server injects inline scripts, so a strict `script-src 'self'` in the
source HTML would break `npm run dev`. The policy is added by a build-only plugin
(`slip-csp` in `vite.config.ts`). Production HTML always carries it; dev never does.

### D-06 — `style-src 'unsafe-inline'` is present, and why that is acceptable
Tailwind is a compiled stylesheet, not inline styles — but React (and any future
inline style attribute) needs `unsafe-inline` for `style`. The XSS risk that matters
is script execution, which stays locked to `'self'`. No `unsafe-eval` anywhere.

### D-07 — `connect-src` is scheme-limited, not host-limited
A merchant can point slip at their own explorer or rate source, which cannot be
enumerated in a static policy. So CSP allows `https: http: ws: wss:` and the
provider layer separately enforces the merchant's configured allow-list, logging any
refusal. Tightening CSP per-install requires a code change, which is what we want:
the shipped artifact is uniform.

### D-08 — Networks are chosen, never inferred
Signet, Testnet3 and Testnet4 share byte-identical address encodings (`tb1…`). No
prefix can identify them. The merchant picks the network; validation always takes a
`NetworkId`. Encoded in `src/core/network.ts` with a test that asserts the collision.

### D-09 — SLIP-132 prefixes live in `keys.ts`, not `network.ts`
A prefix does not uniquely name a coin, so it cannot be part of a coin/network table
without inventing an answer. Table and parser share one module (`src/core/keys.ts`),
pinned to the SLIP-0132 registry by a test that asserts every version byte.

### D-10 — A prefix suggests a script type; the merchant confirms it
SLIP-0132 registers `Ltub`/`ttub` as "P2PKH **or** P2SH", and Bitcoin's `xpub` is
equally ambiguous between legacy and nested segwit. So `resolveScript()` returns a
*suggestion* plus warnings, and the derivation-preview gate is where the human
settles it. Silently choosing would be a guess about somebody's money.

### D-11 — `zpub` and `vpub` are coin-ambiguous, and we say so in the UI
Litecoin native segwit has **no registered prefix** — LTC wallets reuse Bitcoin's
`zpub` (0x04b24746) and `vpub` (0x045f1cf6). The same key therefore produces `bc1…`
or `ltc1…` depending only on the coin the merchant picked. slip never infers the
coin from the prefix; it warns that the prefix is shared and derives for the chosen
chain. A test asserts the same zpub yields different addresses per coin.

### D-12 — Bitcoin Core is the address oracle, not our own library
`tests/vectors/core-derived.json` is generated by `scripts/make-core-fixtures.mjs`
using `bitcoin-cli deriveaddresses` (v28) for pkh / wpkh / sh(wpkh) / tr /
`wsh(sortedmulti(2,…))`. A library agreeing with itself proves nothing; agreeing with
Core proves interop. LTC is checked by parameter substitution — same hash160, Litecoin
version bytes / `ltc1` HRP — because no public Litecoin oracle is available offline.

### D-18 — BIP-85 is implemented as imported child accounts, never on-device
BIP-85 derives child entropy from the *master private key*, so no watch-only app can do
it. slip's "counters" are the honest equivalent: the merchant derives a BIP-85 child
seed on their own signer (Coldcard/Sparrow/Krux/Jade), imports it as a wallet, exports
that wallet's account xpub, and pastes it here as e.g. "Front counter". Each account
keeps its own index, its own first address and its own hand-off, with no path back to
the master key on this device. Claiming on-device BIP-85 would mean asking for a master
key — the one thing this product exists to never see.

### D-19 — A counter is unusable until address 0/0 is acknowledged
`acknowledgedAt` is null on creation and set only by an explicit "I compared address 0/0
with my wallet" action. Staff hand-off is refused while it is null, so a wrong derivation
cannot reach a customer by way of a staff member in a hurry. The check is re-openable,
and the first address is stored so it can be re-shown without re-deriving.

### D-20 — The till PIN gates people, not money
PBKDF2-SHA256, 200k iterations, 16-byte random salt per PIN, constant-time compare,
stored as `pbkdf2$iter$salt$hash`. It names who is holding the device and blocks a
silent counter switch; it can never sign, spend or recover anything. Hand-off requires a
named person, and switching counters mid-shift requires the PIN.

### D-16 — The currency table is GENERATED from ISO 4217, never typed
`src/core/currencies.ts` is produced by `scripts/make-currency-table.mjs` from the
published `datasets/currency-codes` CSV (165 currencies). Minor-unit exponents are
the classic transcription trap: type `JPY: 2` and every yen price is 100× too small,
type `KWD: 2` and a dinar price loses its third decimal. Generated, with the script
committed so it can be re-run and audited.

### D-17 — Two arithmetic bugs the golden table caught before any merchant did
1. **Tax-inclusive extraction was wrong.** `taxOnNet` treated an inclusive amount as a
   NET base instead of a gross total, so it under-reported tax (87 vs 88 on a
   10.875%-inclusive 10.88). Inclusive now derives the net and takes the remainder, so
   `net + tax` always equals the total exactly.
2. **The fixture asked for impossible input.** A `199.00 VND` case assumed two
   decimals for a zero-decimal currency; the parser refused it. The parser was right —
   the fixture was fixed, which is the point of cross-checking two implementations.
Both were found by the independent Python reference, not by review.

### D-13 — CSP authorises the inline bundle by HASH, never `unsafe-inline`
A single-file build has no external script to allow: the whole app is one inline
`<script>`, which `script-src 'self'` blocks outright (found live the first time the
site was served — the app still rendered because the *module* script had been
authorised, but a second inline script was refused). `'unsafe-inline'` would fix it
and re-open XSS, so the build computes the SHA-256 of each inline script from the
FINAL written HTML and pins those hashes in the policy. Only the shipped bytes run.

Consequence: any script a network edge injects into the page at serve time is
**refused** — which is the behaviour we want, and is exactly what happens on the
custom domain (see D-14).

### D-14 — `frame-ancestors` is a header, not a meta tag
Browsers ignore `frame-ancestors` in a `<meta>` policy and log a warning about it,
so it moved to `public/_headers` (Cloudflare Pages serves it as a real header) along
with `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` and
`X-Content-Type-Options`. Verified in the live response headers, not just the file.

### D-15 — The custom domain is not byte-identical to the build; `*.pages.dev` is
Cloudflare injects its bot-detection snippet (`/cdn-cgi/challenge-platform/scripts/jsd/main.js`)
into HTML served through the giveabit.io zone. Measured: `slip-6d6.pages.dev` returns
a file whose SHA-256 equals our build exactly, while `slip.giveabit.io` returns the
same document plus that injected `<script>`. Our CSP refuses the injected script
(confirmed: the only network request the page makes is its own URL), so no third-party
code runs — but the served bytes differ from `SHA256SUMS` on the custom domain.
**A merchant verifying the artifact must compare against the pages.dev download or a
repo copy, not the proxied domain.** Turning bot JS-detection off for the zone would
make the bytes match; that is a family-wide security setting and not ours to flip.

### D-21 — The wizard guides, it does not gate
A shop owner should be walked through five screens; a stranger evaluating slip should still
be able to read the page. So the wizard opens from a button (`set up your shop`) rather than
taking over the first visit, and `skip to the workbench` is always available. The *rule* that
matters — you cannot leave the wallet step until address 0/0 is confirmed — lives in
`core/settings.ts` as a pure `gateFor()` function with tests, not as a disabled attribute a
refactor can drop.

### D-22 — v0.6.0 was bumped but never published
A deploy run was interrupted after `npm version minor` and before the upload, so the next
publish is v0.7.0. `CHANGELOG.md` lists only versions that actually reached the live origin
(the script appends on success only), so a gap in the numbers is the honest record — not a
missing entry.

### D-23 — Panels share one store through a DOM event, not duplicated state
Counters, Backup and Settings all read the same localStorage. Each held its own copy, so a
counter added in one panel was invisible to another — which is exactly how a backup shipped
*without the counter it was meant to protect*. They now re-read on a `slip:data-changed`
event. Reading and announcing are separate functions: a panel that dispatches must not also
listen, or it refreshes itself forever.

### D-24 — The backup carries the PIN hash
A restore used to bring back counters and the shift log but not the PIN, leaving a "new"
device with the hand-off protection silently absent. The PIN hash now travels in the
encrypted state, and a browser test proves the full loop: set PIN → export → wipe → restore
→ a hand-off is still refused without the PIN.

### D-25 — CI and the artifact scan mirror `deploy.sh`
GitHub Actions runs typecheck, lint, tests, build, then `scripts/scan-bundle.sh`, which fails
on `eval(`, `new Function`, tracker hosts, private-key-shaped strings, and any claim of a
payment the engine cannot observe. A green CI now means the artifact *could* be published,
not merely that the source compiles.

### D-26 — "Wallet" is the unit; a till is one *purpose* of a wallet
Cam holds several wallets for different reasons: his employer's (BIP-85 child), his parents'
(multisig or BIP-85), his own (a single pubkey). They are all watch-only, so the same record
serves all of them — with `purpose` and `colour` as local labelling only, never derived and
never sent anywhere. A "counter" is now just `purpose: 'till'`.

### D-27 — Four kinds of material, four honest labels
An xpub (a chain of addresses), a descriptor (policy, including multisig), a single public
key (exactly one address, cannot rotate), and a plain address (cannot rotate, cannot be
verified as yours). The last two warn at paste time, because "one address forever" is a
privacy decision, not a detail.

### D-28 — Public explorer by default, endpoint is a setting
`mempool.space` for Bitcoin (all three networks except testnet3 default) and
`litecoinspace.org` for LTC mainnet; **Litecoin testnet has no dependable public Esplora and
the app says so** rather than failing silently at sale time. The merchant's own
Esplora/electrs URL goes in Settings. Balances are per *address 0/0*, labelled with their
source and fetch time — never "your wallet balance", which slip cannot know without scanning
a chain it does not index.

### D-29 — Reserve at creation, burn when the address is shown
`createInvoice` only RESERVES an index. The index is burned (`burnInvoiceIndex`) at the moment
the address reaches a payer. That distinction is what lets an abandoned cart hand its index
back — and it is why `cancelInvoice` is honest rather than decorative.

### D-30 — `seen` is not `paid`, and the code cannot confuse them
`statusFromObservation` reads chain and mempool receipts separately. Mined and within 1% of
the amount = `confirmed` (then `complete`, with a receipt). Mempool only = `seen`, labelled
"not mined yet". Overdue and short = `underpaid`. A late but full payment still completes,
because reality beat the clock.

### D-31 — Manual confirmation is a first-class, labelled state
"I have the money" sets `manual: true` and the receipt says *marked paid by you* plus *slip did
not observe this payment*. Cash is a real thing in a real shop; the dishonesty would be
pretending the till saw it.

### D-32 — `window.slip` is read-only by construction
The agent surface returns copies from storage and emits events. There is no method that writes,
signs or sends, so a future bot can report and reconcile but can never move money. Tests assert
`readOnly === true`.

### D-33 — Lightning is LNURL-pay against the merchant's own address, never a node
slip asks the merchant's Lightning address for an invoice at the exact amount. Settlement is
only reported when that wallet's own `verify` URL returns `settled: true`. A wallet that offers
no verify URL is labelled unverifiable and falls back to a manual confirmation — a Lightning
payment nobody can check must not look checked.

### D-34 — A day digest is computed locally; stamping is opt-in and never called a confirmation
`dayDigest` hashes completed invoices for one date into a deterministic SHA-256 (sorted ids, no
timestamps inside the hash). Submitting it to a calendar is a separate, explicit action, and the
wording that follows is "submitted", not "confirmed": the Bitcoin attestation arrives in the
calendar's own time and slip will not claim it early.

### D-35 — Pairing is public material, and imports arrive unchecked
The app has nothing secret to move, so pairing is a QR of an xpub/descriptor/address. The
receiving device deliberately does NOT acknowledge address 0/0: it has not compared anything
against the owner's wallet, and `UNCHECKED` on screen is the only honest state until a human looks.

### D-36 — A rate has an age, and a stale rate is refused
Quotes carry `fetchedAt`, `ageSeconds` and `stale`; `requireFresh` is called before pricing and a
stale quote stops the sale with a plain sentence. The source shown is the endpoint that actually
answered — a merchant pointing at their own node must never be told the number came from
mempool.space.

### D-37 — One rate request per minute, deduplicated on the promise
A remount (React StrictMode, or a panel re-render) joins the in-flight request instead of
starting a second one. Asking a price feed four times a minute is a privacy leak and a way to be
rate-limited exactly when a queue forms. A failed request is evicted so the next attempt is real.

### D-38 — The customer screen is a second window of the same file
`?display=1` renders only the QR, the amount and the status, and reads nothing from the books.
It is fed over `BroadcastChannel`, which never leaves the device; if the channel is unavailable
the screen says it is not connected rather than showing a stale total.

### D-39 — The backup carries the books
Accounts, PIN and shift log were never enough: the invoices are what a merchant cannot recreate.
The `.slip` file now includes the ledger in the same wire shape the app already writes (decimal
strings, so no precision loss), and the restore message states whether the file had them.

### D-40 — Receipt proofs are records, not signatures
`SLIP1|…` names the invoice, address, amount, time and (when anchored) the day digest. slip holds
no key that could sign, so the proof is honest about being a record; the Check-a-receipt panel
compares it against the local books and refuses to call an unknown proof "checked".

### D-41 — A refund is a record, never a transaction
slip has no keys, so it cannot send money back. `checkRefund` caps a refund at what was received
minus what was already refunded, and every refund names its method (on-chain, Lightning, cash,
goodwill) so the day close can separate money that left the wallet from money that left the drawer.
The UI states that slip did not move anything.

### D-42 — A swept payment is `complete`, not `confirmed`
The reconciliation sweep promoted a mined, fully-covered invoice to `confirmed` — which the day
close ignores, because only `complete` sales are takings. A sale could therefore be paid, receipted
and invisible in the Z-report. The sweep now runs `completeIfConfirmed` and a test locks it.

### D-43 — Silent Payments can never be watched by slip, and the UI says so
Detecting an sp1 payment needs the wallet's scan key. slip refuses private material, so an sp1
address is a receive destination only: validated, shown as a BIP-21 QR, and recorded as a manual
confirmation. Claiming auto-detection would require breaking the one rule.

### D-44 — A split sale is one sale
Both legs are ordinary invoices with their own reserved index, but the receipt is only issued when
both are complete — half a payment must not look like a finished sale.

### D-45 — Printing goes through a Blob, not `document.write`
The bundle scanner bans `document.write`, and rightly: it is how an injection becomes executable.
Printable receipts and close sheets are built as HTML strings in their own window via a Blob URL,
white background and black text because paper is ink.
