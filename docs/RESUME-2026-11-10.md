for, but that make the till look like it was made by hand.

## The 44/48 split and the silent buttons (v0.31.34)

**The floor is now two floors, decided once.** 44px for anything a finger may hit; **48px for the
things that move money** — the primary, the charge bar, the amount keys. `tap-audit` enforces both:
a primary under 48 is a failure, a non-primary between 44 and 48 is a warning it prints. Measured
after: 0 hard failures, 158 between 44 and 48, all listed.

**Three silent buttons stopped being silent.** `AmountPad` ("Add to the sale"), `Counters` ("Save
counter") and every `ConfirmButton` (the restore that replaces the device) used `disabled`, which
dims the control and removes its focus — so the reason printed underneath could not be reached by a
keyboard. All three are `aria-disabled` with a guarded click and a `.v2-blocked` dimming class; the
blame lines were already there and now do their job. Still to convert: `AnchorPanel` (publish an
anchor) and two `Backup` buttons that have no blame line yet.

**v1 was not deleted, on purpose.** Removing the old skin is 102 `isSkinV2()` branches across the UI,
not a flag flip. Doing that in the tail of a session, with the browser suites already spent, would be
exactly the kind of half-redesigned product the brief warns about. It gets its own pass, with the
full gate budget, and the owner's go — the tag and the passing revert proof are already in hand.

**The live run found a Cloudflare injection (2026-11-11).**

Run against https://slip.giveabit.io, the offline suite passed every check but logged two console
errors:

    Executing inline script violates the following Content Security Policy directive
    'script-src 'self' 'sha256-jLWqHz+…'' … blocked.

Cause: Cloudflare injects its own inline scripts at the edge — the body contains `__CF$cv$params`,
which is the **JavaScript detections** part of Bot Management. slip's CSP pins exactly one inline
script (the bundle) by hash, so the injected ones are refused. Nothing breaks visibly: the page is
ours, the injected script simply never runs, and the count in the footer stays 0.

Two questions this settles:

1. **Is it slip's bug?** No. The build ships one inline script and the app renders, so a refusal can only
   be a second, foreign script. The suite now says so in a `NOTE` line instead of failing, and a local run
   (no Cloudflare) stays strict — proven by running both.
2. **Should it be fixed?** Only in the Cloudflare zone: turn off JavaScript detections / Bot Fight Mode
   for `slip.giveabit.io` (a hostname-scoped rule), or accept the console noise. **Not flipped** — a
   zone-wide bot setting is the owner's call, and the memory note says so.

**v0.31.53 — an icon is a contract with the launcher.**

A merchant tried to put slip on a phone and got a *shortcut* instead of an app, wearing the browser's own
icon. Not a browser quirk: the launcher contract was wrong.

| Was | Why it failed | Now |
| --- | --- | --- |
| one icon, **300×220 wordmark**, marked `any maskable` | Android needs a **square 192** and **square 512**; `maskable` demands square art inside the safe zone. Unsatisfied requirements = no install prompt | `icon-192.png`, `icon-512.png`, `icon-maskable-512.png` (512, art at 46% so a circular crop cannot bite) |
| no `apple-touch-icon` at all | **iOS ignores manifest icons entirely** — it reads `<link rel="apple-touch-icon">`. Missing = the grey default | `apple-touch-icon.png`, 180×180, opaque (iOS composites transparency onto black) |
| favicon was the 300×220 wordmark | a wordmark is unreadable at 16px and unusable as a shortcut icon | `favicon-32.png`, the receipt mark |
| `theme_color`/`background_color` still the pre-redesign `#0b0d10` | launch flash in the wrong colour | `#24201c` |

The icon is drawn from **the app's own mark** (`src/ui/Brand.tsx`, variant `mark`) by
`scripts/make-icons.mjs`, so it cannot drift from the thing it represents. Orange `#f5820a` tile, ink
receipt: verified in pixels — background at the corners, art centred, nothing within 1px of an edge.

Proof, asked of Chromium itself rather than assumed: `tests/e2e/installable.mjs` (**suite 16**) calls
`Page.getInstallabilityErrors` and requires **zero** errors, plus every icon served as `image/png`, square,
the apple-touch-icon present, and the worker registered. Lesson written into the suite: **Playwright
contexts are incognito, and Chromium refuses to judge installability in incognito** — the suite uses a
throwaway *persistent* profile instead.

**v0.31.56 — the customer QR stopped sitting on its own words.**

Cam: *"The QR code is overlapping the text and cannot be seen very well."* Measured, not guessed: on the
Manual panel the pocket was **112px** and the SVG inside it was drawing **132px**, 20px over on both axes,
straight across the paragraph beside it — at 390 **and** at 1440.

The cause is general, not a stray number: `renderQrSvg` draws at the module count × its own `scale`, so the
code's pixel size changes with how much data it carries, while the box stayed fixed. **The box must own the
size.** New `.qr-pocket` in `src/index.css`: `overflow: hidden`, white background, 6px padding, and
`.qr-pocket > svg { display:block; width:100%; height:auto }` — the code scales to fit and is never cropped,
because a cropped code looks fine and cannot be scanned.

Applied to **four** places that had the same fault, not just the one reported:

| panel | was | now |
| --- | --- | --- |
| Manual (the customer QR) | 112px box, 132px code | 128px pocket, 116px code, clears the words |
| Verify (a proof code) | 144px box, code at 45 modules | 132px, inside |
| Silent Payments | 192px box, code at `scale: 5` | fits the pocket |
| Lightning | 192px box, code at `scale: 5` | fits the pocket |

`tests/e2e/guide.mjs` now pins three things on the Manual code: it is drawn **inside** its pocket, it
**does not cross** the paragraph beside it, and it is at least 100px — because a code that is visible but
too small is the same failure as an invisible one. The code was also **decoded** (jsQR) to
